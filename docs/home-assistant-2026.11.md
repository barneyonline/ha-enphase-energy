# Home Assistant 2026.11 and Enphase Energy

The minimum version is 2026.11.0. This review covers the 2026.11 release notes, the 2026.11.0 and 2026.11.2 Core sources, and the Enphase integration. Marketplace installation, frontend rendering, and Enphase hardware still need live verification. [Home Assistant 2026.11 release notes](https://www.home-assistant.io/blog/2026/11/04/release-202611/)

## Compatibility and setup

- Docker and CI pin `homeassistant==2026.11.0` and the matching `pytest-homeassistant==2026.11.0`. Core extracted its shared pytest helpers and fixtures into a standalone plugin. [Core fixture extraction](https://github.com/home-assistant/core/pull/186956) · [Core plugin setup](https://github.com/home-assistant/core/pull/187095) · [Repository Docker dependencies](../devtools/docker/requirements-dev.txt)
- Register cached device metadata through `async_get_or_create_from_info()` with native `DeviceInfo` objects. This preserves the distinction between an omitted field and an explicit `None`. [Core dataclass change](https://github.com/home-assistant/core/pull/180251) · [Device registry API](https://contributors.home-assistant.io/core/integrations/device-registry/)
- The options flow uses Probatio directly and uses Home Assistant's conditional field markers for Export Limit Defaults, Authentication, Grid Mode, and Envoy History Migration. Core omits hidden inputs before validation, including stale submitted values. The handlers still check capabilities and require confirmation before commands or migrations. [Flow forms](https://contributors.home-assistant.io/core/integrations/flow-steps/#fields-that-show-based-on-another-field) · [Core initialization](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/__init__.py) · [Enphase options flow](../custom_components/enphase_ev/options_flow.py)
- Reauthentication and reconfiguration use Core's update-and-abort helper directly when an entry has an update listener. Entries without a listener use the native helper that schedules a reload. The config, options, and repair flow result builders already specify their step IDs. [Core config entry flow](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/config_entries.py) · [Flow result step IDs](https://contributors.home-assistant.io/blog/2026/10/23/flow-results-require-step-id/) · [Enphase config flow](../custom_components/enphase_ev/config_flow.py)
- Entry-owned Repairs and in-place site-sensor entity-ID renames use the native lifecycle APIs. Repairs preserve dismissals during reloads, and renamed sensors retain their timers and listeners. [Enphase PR #987](https://github.com/barneyonline/ha-enphase-energy/pull/987) · [Core repair ownership](https://github.com/home-assistant/core/pull/186197) · [Core entity ID lifecycle](https://github.com/home-assistant/core/pull/183946)

## Action target exclusions

- Core applies `target.exclude` after expanding the positive target. The Enphase router applies device exclusions to device-level actions and rejects fully excluded targets before dispatch. Schedule sync accepts native Home Assistant targets and continues to accept `device_id` in the action data. [Core target helper](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/helpers/target.py) · [Enphase action schemas](../custom_components/enphase_ev/services.py) · [Enphase service router](../custom_components/enphase_ev/service_routing.py)
- When exclusions are present, `site_id` and `config_entry_id` narrow the remaining sites. For tariff actions with a Home Assistant target, those fields also narrow the positive selection when exclusions are absent. Tariff shorthand uses one eligible rate entity. An explicitly selected tariff rate batch fails before dispatch if it contains an excluded entity or a rate from a different site than the target. Use a device exclusion to drop a whole charger from an area or label selection, since removing one entity leaves the device eligible through a device-level target. [Core target helper](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/helpers/target.py) · [Enphase service router](../custom_components/enphase_ev/service_routing.py) · [Enphase action definitions](../custom_components/enphase_ev/services.yaml)

## Marketplace and names

- New installs start in Marketplace, where the manifest classifies Enphase Energy under Solar & Batteries and EV Charging. Home Assistant migrates existing HACS installations and update entity IDs. The Marketplace catalog includes `barneyonline/ha-enphase-energy` via `hacs/default`, and publishing still uses `hacs.json`. [Marketplace user documentation](https://www.home-assistant.io/integrations/marketplace/) · [Integration categories](https://contributors.home-assistant.io/core/integrations/categories/#energy) · [Catalog entry](https://github.com/hacs/default/blob/master/integration)
- Home Assistant computes names from the entity, device, and optional parent and area context. The main charging switch takes its name from its charger. Grouped battery sensors use the discovered unit name or serial, and grouped inverter sensors include the serial. Child devices describe logical parts of a single product. Enphase's grouped devices represent separately serialized equipment, and the recorded charger API shows connector 1. [Naming changes](https://www.home-assistant.io/blog/2026/11/03/naming-things-in-home-assistant/) · [Child devices](https://contributors.home-assistant.io/core/integrations/device-registry/#child-devices) · [Enphase charger API](api/api_spec.md)

## Diagnostics and energy troubleshooting

- The integration's debug banner now offers **Show logs** with integration-scoped live output. Core filters by the integration's package path and manifest logger namespaces, which already cover Enphase's logger. Use this in support instructions alongside the existing config-entry and device diagnostics. [Release notes for live logs](https://www.home-assistant.io/blog/2026/11/04/release-202611/#live-logs-for-each-integration) · [Core log stream](https://github.com/home-assistant/core/pull/185595) · [Enphase manifest](../custom_components/enphase_ev/manifest.json)
- **Tools → Action history** gives administrators access to recorded action inputs, including the `otp` passed to `enphase_ev.set_grid_mode`. Core publishes the submitted data in `call_service` and the history endpoint returns it. Keep Grid Mode action data out of support attachments. A masked text control or `probatio.Secret` can address display or validation error rendering but does not remove the submitted data from Action history. [Core service call](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/core.py) · [Core Action history endpoint and payload](https://github.com/home-assistant/core/pull/187344) · [Probatio validation guidance](https://contributors.home-assistant.io/core/development/input-validation/#secrets) · [Enphase Grid Mode action](../custom_components/enphase_ev/services.yaml)
- Home Assistant can create or reuse an energy helper when an eligible source has only a power entity. Use Enphase's existing native energy totals when available. If a bad sample already affected statistics, **Tools → Statistics** can now delete a selected time range. That operation repairs the recorded window. Integration-side sample acceptance still governs future readings. [Power-to-energy helper](https://www.home-assistant.io/blog/2026/11/04/release-202611/#from-power-to-energy-in-one-step) · [Statistics range deletion](https://github.com/home-assistant/core/pull/186071) · [Enphase energy handling](architecture.md)

## Config-entry lifecycle

- During initial entry setup on a running Home Assistant instance, Core carries the Enphase rate-limit backoff into the setup retry schedule. The regression sends a mocked HTTP 429, checks the delay, then observes successful automatic setup. [Core first-refresh retry handling](https://github.com/home-assistant/core/pull/185521) · [Enphase refresh logic](../custom_components/enphase_ev/coordinator.py)
- Config-entry unload uses `async_unload_platforms_or_raise()`. Core supplies the translated failure and the integration retains its runtime when a platform unload fails. [Core unload helper](https://github.com/home-assistant/core/pull/185989) · [Enphase config-entry setup and unload](../custom_components/enphase_ev/__init__.py)
- Startup tasks use Home Assistant's named background-task API and remain owned by the entry runtime for cancellation during unload. [Core task API](https://github.com/home-assistant/core/blob/2026.11.0/homeassistant/core.py) · [Enphase refresh runner](../custom_components/enphase_ev/refresh_runner.py)

## Other APIs reviewed

- Firmware advisory entities derive availability by comparing reported and catalog versions. Core's `has_update` override is useful when a provider offers an independent update-available signal. Enphase's rollout and upgrade-status fields describe the rollout and its progress, while the version comparison remains the availability source. [Core update availability](https://contributors.home-assistant.io/blog/2026/10/10/update-entity-update-availability/) · [Enphase firmware entities](../custom_components/enphase_ev/update.py)
- The unit selector is for a configuration choice between compatible units. Enphase's configurable polling intervals, voltage, export limit and slew rate use fixed input units with the Enphase API. [Core unit selector](https://contributors.home-assistant.io/blog/2026/10/09/uom-selector/) · [Enphase options flow](../custom_components/enphase_ev/options_flow.py)
